# @o-t-p-y/mcp

سرور رسمی Model Context Protocol (MCP) برای [OTPy.ir](https://otpy.ir) — تعامل با حساب OTPy، مشاهده مصرف، ارسال کد آزمایشی و مدیریت کلیدها مستقیماً از داخل دستیارهای هوش مصنوعی.

## دو نوع اعتبار

این سرور می‌تواند از دو اعتبار متفاوت استفاده کند که هر کدام کاربرد جدایی دارند:

| اعتبار | متغیر محیطی / فلگ | کاربرد |
|---|---|---|
| **کلید API** (پروژه‌محور) | `OTPY_API_KEY` / `--api-key` | احراز هویت API پیامک و مصرف: `get_usage`، `send_test_otp`، `verify_test_otp`. همان کلید `otpy_...` است که برای ارسال OTP واقعی در محصول استفاده می‌کنید. |
| **کلید کاربری** (کاربرمحور) | `OTPY_USER_KEY` / `--user-key` | احراز هویت خواندن پروژه و کنترل زنده‌ی اسکوپ ابزارهای صورتحساب/نوشتن. این سکرت جداگانه‌ی `otpy_uk_...` را از صفحه‌ی **Integration** (`/integrate`) در [dash.otpy.ir](https://dash.otpy.ir) بگیرید. |

ابزارهای فقط-خواندنیِ APIمحور (`get_usage` و `get_integration_snippet`) فقط کلید API می‌خواهند. خواندن پروژه‌ها (`list_projects` و `list_otp_messages`) به کلید کاربری فعال نیاز دارد و `list_transactions` علاوه بر آن اسکوپ `billing` می‌خواهد. هر ابزارِ نیازمند کلید کاربری، بدون آن رد می‌شود.

## نصب / راه‌اندازی

### Cursor

به فایل `.cursor/mcp.json` یا Cursor Settings → MCP اضافه کنید:

```json
{
  "mcpServers": {
    "otpy": {
      "command": "npx",
      "args": ["-y", "@o-t-p-y/mcp"],
      "env": {
        "OTPY_API_KEY": "otpy_your_api_key_here",
        "OTPY_USER_KEY": "otpy_uk_your_user_key_here"
      }
    }
  }
}
```

### Claude Desktop

به `claude_desktop_config.json` اضافه کنید:

```json
{
  "mcpServers": {
    "otpy": {
      "command": "npx",
      "args": ["-y", "@o-t-p-y/mcp"],
      "env": {
        "OTPY_API_KEY": "otpy_your_api_key_here",
        "OTPY_USER_KEY": "otpy_uk_your_user_key_here"
      }
    }
  }
}
```

می‌توانید اسنیپت آماده MCP (برای Cursor، Claude Desktop، Windsurf و Kilo) را از صفحه‌ی **تنظیمات پروژه** (`/project-settings`) در [dash.otpy.ir](https://dash.otpy.ir) کپی کنید. ساخت خودِ کلید کاربری در صفحه‌ی **یکپارچه‌سازی** (`/integrate`) انجام می‌شود.

## مدل اسکوپ (`user_keys`)

هر کلید کاربری دقیقاً دو اسکوپ مستقل دارد — `write` و `billing` — به‌علاوه فلگ `root` که همیشه به‌صورت مشتق `write AND billing` محاسبه می‌شود و هرگز مستقیم تنظیم نمی‌شود. هیچ مجوز سوم جداگانه‌ای وجود ندارد.

| اسکوپ | دسترسی |
|---|---|
| `write` | `send_test_otp`، `verify_test_otp`، `create_api_key` |
| `billing` | `get_balance`، `list_api_keys`، `list_transactions` |
| `root` (مشتق: هر دو فعال) | همه موارد بالا — فقط مخفف «هر دو را دارد»، نه اسکوپ جدا |

کلید کاربری با اسکوپ‌های موردنیاز را در صفحه‌ی **Integration** (`/integrate`) داشبورد بسازید (ساخت/لیست/لغو و تغییر `write`/`billing` همه آنجاست). سکرت خام `otpy_uk_...` فقط یک بار هنگام ساخت نمایش داده می‌شود — بلافاصله آن را در `OTPY_USER_KEY` کپی کنید.

### تأیید اسکوپ چگونه کار می‌کند

هر فراخوانی ابزارِ محافظت‌شده با `write` یا `billing` یک **درخواست شبکه واقعی و زنده** به `GET /v1/user-keys/self` روی API می‌زند و `OTPY_USER_KEY` شما را به‌عنوان Bearer ارائه می‌دهد. API آن را هش کرده و ردیف زنده جدول `user_keys` را بررسی می‌کند — اسکوپ‌های این اعتبار هرگز نمی‌توانند به‌صورت محلی جعل یا دور زده شوند. اگر کلید لغو شود یا اسکوپ‌هایش در داشبورد کم شود، همان فراخوانی بعدی بلافاصله آن را منعکس می‌کند؛ هیچ کش محلی از اسکوپ‌ها وجود ندارد.

**هیچ دورزدن سمت کلاینتی وجود ندارد.** نسخه‌های قبلی این سرور فلگ محلی `OTPY_MCP_WRITE` / `--write` داشتند که فقط در کانفیگ همین پروسه زندگی می‌کرد — هرگز سمت سرور تأیید نمی‌شد، پس هر کسی با دسترسی به env کلاینت خودش می‌توانست آن را ست کند و گیت ابزارهای نوشتن را دور بزند. آن فلگ کاملاً حذف شده است. اگر هنوز `OTPY_MCP_WRITE`/`--write` در کانفیگ قدیمی دارید، الان کاملاً بی‌اثر است: `parseConfig` اصلاً آن را نمی‌خواند، و تنها چیزی که دسترسی write/billing می‌دهد یک `user_key` واقعی با اسکوپ متناظر است که در هر فراخوانی از طریق شبکه تأیید می‌شود.

اگر اصلاً `OTPY_USER_KEY` تنظیم نشده باشد، همه ابزارهای کاربرمحور رد می‌شوند (fail closed) — فقط ابزارهای بدون اسکوپ (`get_usage`، `get_integration_snippet`) با کلید API پروژه کار می‌کنند.

### گرنت‌های پروژه

یک کلید کاربری می‌تواند به پروژه‌های مشخص محدود شود (`user_project_grants`، در همان صفحه‌ی Integration). قاعده:

- **صفر ردیف گرنت** → نامحدود: کلید روی هر پروژه‌ای که مالکش به آن دسترسی دارد کار می‌کند.
- **یک یا چند ردیف گرنت** → محدود به دقیقاً همان شناسه‌های پروژه.

هر فراخوانی ابزاری که آرگومان `project_id` دارد، این را همراه با چک اسکوپ بررسی می‌کند (همان درخواست شبکه زنده) و اگر کلید به آن پروژه گرنت نشده باشد، فراخوانی رد می‌شود.

## ابزارها

| ابزار | اسکوپ لازم | توضیح |
|---|---|---|
| `get_usage` | ندارد | مصرف امروز یا بازه‌ی شامل ابتدا و انتها تا ۹۰ روز |
| `list_projects` | کلید کاربری | فهرست پروژه‌های قابل مشاهده برای کلید کاربری |
| `list_otp_messages` | کلید کاربری | فهرست پیامک‌ها؛ status داخلی است و `verified_at` تایید را مشخص می‌کند، نه تحویل اپراتور |
| `list_transactions` | `billing` | فهرست تراکنش‌های کیف پول به تومان |
| `get_balance` | `billing` | موجودی فعلی کیف پول |
| `list_api_keys` | `billing` | لیست کلیدهای API پروژه و محدودیت‌ها |
| `get_integration_snippet` | ندارد | تولید اسنیپت کد آماده (nodejs، python، go، php، curl، csharp) |
| `send_test_otp` | `write` | ارسال کد OTP آزمایشی به یک شماره |
| `verify_test_otp` | `write` | تایید کد OTP آزمایشی |
| `create_api_key` | `write` | ساخت کلید API جدید با محدودیت‌های دلخواه |

اسنیپت‌های ادغام همیشه `OTPY_API_KEY` را از محیط اجرا می‌خوانند؛ سرور MCP هرگز کلید API خام پیکربندی‌شده را داخل کد تولیدشده قرار نمی‌دهد.
